RSI（Recursive Self-Improvement，递归自我改进）最近非常火。它的基本想法其实很简单：如果 AI 能设计出一个比自己更聪明的 AI，那么下一代的 AI 是不是又能设计出更强的下一代？由此引申出一个听起来有点可怕、却又极其吸引人的想法——我们能不能让 AI 自己迭代自己，一代一代不断升级，最终远远超出人类的智慧？最近 Geoffrey Hinton、Yoshua Bengio，加上 OpenAI、Anthropic 的一众研究者写了一篇文章来讨论这个 RSI 的问题。本文以这篇文章为切入点，把 RSI 这条线的相关工作捋一遍，重点落在两件事上：一是这些工作里有多少是真正的进步，二是智能爆炸离我们到底还有多远。

核心要点

  • RSI 有两条主线：改 foundation model（更新参数）和改 harness/scaffolding（改 prompt、tool、memory，参数不变）。最近的工作更多集中在 harness 自进化。
  • 一个被反复验证的前提：只有当底层模型能力足够强时，迭代 harness 才有效；弱模型迭代 harness 反而会让性能下降（STOP 实验里 GPT-4 越迭代越好，GPT-3.5/Mistral 越迭代越差）。
  • 收益归因的冷水：Amazon + NPU 的工作把 harness 进化的收益拆成过拟合、test-time scaling 和可泛化改进三类，发现大量收益其实是前两者——Meta-Harness 甚至在 ALFWorld 上把一个 0.8B 模型「进化」到 100%，代价是把 LM 整个扔掉、退化成一个 503 行的规则引擎。
  • 智能爆炸的判断：Hinton、Bengio 等认为 software-driven intelligence explosion 已有初步证据是可能的，递归反馈回路正在形成。他们警告社会可能来不及适应、人类监管会失效、权力制衡会被侵蚀，「行动的窗口可能关闭」。

一、智能爆炸与哥德尔机

「智能爆炸」（intelligence explosion）这个概念最早可以追溯到跟图灵同时代的数学家 I.J. Good。他在 1965 年发表的文章里讨论了 intelligence explosion，也就是后来常说的 technological singularity（科技奇点）。Good 的论述更多是一种推测或预言：他认为超人类智能（superhuman intelligence）的到来，可能来自于一种能够自我改进的机制。他把超智能（ultra-intelligent）定义为能超过所有人类智力的机器；而设计这种机器本身就是一种智力活动，所以这种超智能机器应该能设计出更好的机器。一旦机器能设计出更好的机器，智能爆炸就会出现（Good 用了一个词：unquestionably）。他还说了一句很重的话：这种超智能机器可能是人类最后所需要发明创造的东西——因为有了这样的机器之后，人再不需要创造任何其他的东西了。

那具体怎么造一个能自我改进的机器？2023 年，LSTM 之父提出过一个叫哥德尔机（Gödel machine）的概念。它受到哥德尔哲学体系里「自指」（self-reference）的启发——一个系统（比如数学系统）能自己理解、研究自己，就叫自指。哥德尔机因此具备两个特点：self-referential（能自指）和 self-improving（能自我改进）。它由两部分组成：problem solver 负责在「找到某种对自己有帮助的改写」这个前提下改写自己的代码；searcher 负责去寻找这种有用的改写。有了这两部分，哥德尔机就能自我改进。不过它更多是一种概念，想法并不特别实际，但它是比较早提出这种自我迭代、自我改进机器系统的，可以算作 RSI 一个非常早期的概念机。

二、RSI 的两个对象与四条线

哥德尔机非常抽象，那具体该如何实现一个能自我改进的机器？同一个 LSTM 之父后来写了一篇专门讨论 self improvement 的综述，里面把 RSI 的对象讲得很清楚。RSI 本质都在递归改进 agents。一个 agent 一般看作两部分：foundation model（大语言模型，作为整个 agent 的内核）和 scaffolding（也叫 harness，就是模型所用的 prompt、tools、memory）。如果只是简单地用裸的大语言模型，它可能无法很好地完成任务——比如 coding agent 如果直接用 LLM，可能缺少查看或修改文件的工具，没有 memory 也发挥不了最大性能。所以一般把 foundation model 和 scaffolding 放在一起作为整体看，这就是一个 agent。

因此 RSI 的 self improvement 也是针对这两方面：第一个是对 foundation model 进行改进（参数会被更新），第二个是对 scaffolding/harness 进行改进（参数不变，只是改 prompt、tool 或 memory）。本节的剩余部分按「foundation model 自改进」和「harness 自进化」两条线展开，每条线挑一两篇有代表性的工作。

Foundation Model 线一：TTRL

传统对大语言模型训练时，不管是预训练还是后训练，基本都需要某种形式的 label——下一个单词、人打的标签、数学题答案。而且这些都发生在 training 阶段，模型一旦训练好，参数就固定了。TTRL 的第一个较大贡献是提出可以在 test time，也就是模型部署之后，继续更新模型参数。当一个大语言模型或 agent 部署到真实环境后还能自己更新参数，这就是自我学习、自我迭代的一种形式，和 RSI 不谋而合。

这里遇到的问题是 test time 的数据往往没有 label。TTRL 用了一个很常见的思路——majority voting：把数据给大语言模型，让它产生很多 prediction 或 rollout，通过 majority voting 取大家一致认为正确的答案作为 ground truth，用来算 reward，再用常用 RL 方法更新模型。参数在这里会更新、会变化。这个方法对大语言模型的涨点非常多，不过主要在比较简单的数据集上。它可看作从 foundation model 角度对大语言模型 self improve 的一种 RSI 形式。

Foundation Model 线二：Agent0

另一篇上个月刚发表的工作叫 Agent0，主打 self evolving agent，from zero data，即不需要任何数据。它的基本思路是两个 agent 互相迭代：一个 agent 出题（curriculum agent，教师），另一个答题（executor agent，学生），「左脚踩右脚」地互相迭代。这套思路也不是 Agent0 首创——类似「agent 出题、agent 答题」的左脚踩右脚迭代，Absolute Zero 那篇 paper 就用过。Agent0 稍有不同的是引入了 tool。curriculum agent 先出题，问题给到 executor agent 答题，学生 agent 答题时会使用工具跟环境交互，据此算 reward；有了 reward 就可以更新教师 agent 或学生 agent，用交替更新的方式实现左脚踩右脚。整个更新过程不需要数据，因为数据都是内部产生的。

这里 tool 的使用和与环境的互动，可能是 RSI 实现一个非常重要的点。一个 agent 如果在封闭体系里自己迭代，应该是有一个天花板的；通过工具跟环境互动，外部信息被注入整个系统，系统获得额外信息，从而能不断自我迭代。

细节上，Agent0 的训练分两步。第一步先训练 curriculum agent（教师）：教师出题，学生答题，答案包括 agent 的工具调用等，用 majority voting 产生 ground truth，进而算 reward。对教师 agent 的更新，reward 采用三个：uncertainty（学生答题做 majority voting 时的不确定性，衡量问题难易，希望教师出的题不太难也不太简单）、tool use（学生解题时 tool 的使用次数，鼓励 tool use）、repetition penalty（让教师出的题尽量不一样，一样的话有 penalty）。教师 reward 是这三者的综合，据此更新教师权重。第二步，教师训练好后权重被固定，转而训练学生 agent：教师出很多题，学生答题，先用 self consistency（和前面 uncertainty 一样）把特别简单和特别难的问题过滤掉，得到一个难度适中的数据集，label 同样通过 majority voting 产生，据此更新学生权重。如此循环，下一次继续训练教师，固定教师权重后再训练学生。

结果上，它和 Absolute Zero 相比涨点明显：4B 模型从 46.4 涨到 52.5，8B 模型从 52.6 涨到 58.2。Agent0 的另一个贡献是强调泛化性——因为题目都是 agent 自己出的，不局限于外部数据，工具也没有特别限制，所以能很好泛化到其他 domain。这至少说明在 foundation model 训练上，「左脚踩右脚、自己出题自己解答」是一条重要思路，但具体怎么评价出题的好坏、怎么产生更好的数据去训练模型，可能是所有这类方法的关键。如果不利用外部数据，内部数据的质量就非常重要。

三、Harness 自进化

前面两篇是 foundation model 如何自我进化，现在切到 harness 这一块。Hugging Face 有一个 blog 标题取得很恰当：「Don't train the model, evolve the harness」（别训模型，进化 harness）。它想表达的观点是：现在模型能力已经相当强，而改进模型开销很大；但对模型周围的 harness 这一块，做的工作比较少，所以值得去做。这个 blog 举了个例子：如果能有一个自动化的 loop，对一个固定的开源模型只优化它的 scaffold，光优化 scaffold 就能从 63.1% 涨到 83% 多，相当可观。

另一个 blog 提了一个有意思的名词：Mismanaged Geniuses Hypothesis（被糟糕管理的天才）。核心意思是现在的 AI model 已经 good enough，之所以能力没发挥出来，是因为没有被 manage 好。作者画了一个卡通图：中间是模型原生能解决的任务范围；如果继续从 foundation model 角度改善，能解决任务的范围可以扩大，但扩大有限；而仅通过 harness 去 manage 这个 LM 能实现的任务扩展区域，远大于对模型 fine tune 带来的提高。有意思的是，作者把 AGI/RSI 那一块画在了最外面——也就是说，作者认为仅靠改善模型本身或改善 manage 可能还不太够，也许还需要一些别的东西。这算是目前 RSI 自进化的两个主流方向：让 foundation model 自我迭代扩充领域，让 harness 自我迭代扩充领域；也许两者结合到某个临界点后，就能进一步实现 AGI。

STOP：递归自我改进的代码生成

先看一篇 2024 年上线、来自 Stanford、Microsoft 和 OpenAI 的文章，提出 recursively self-improving code generation，叫 STOP。核心思想很简单：有一个 agent（有大模型和 harness），文章把这个 harness 叫 improver。它做的事是先用 improver 去看它自己这个 improver 能不能被 improve——把 improver zero 作为输入放进 improver 函数，让它改自己的第一代。在 benchmark 数据集上算各种 task-specific score，最后算出一个 utility。如果这个改变是好的，就选出最好的改进应用到 improver 上，产生第一代 improver one；有了 improver one 再送进它自己，用类似方法自我迭代，得到 improver t。

因为针对 code generation，例子就是改代码。它定义了一个 improve algorithm——既是改进别人的工具，也是自己被改进的对象。improve algorithm 里有一段 prompt（定义它是 expert computer science researcher and programmer，擅长算法优化），提供 initial solution 和 utility，代码返回一个 best solution——注意 best solution 就是一段代码（通过 extract code 产生）。自迭代的意思就是：improve algorithm 产生一个 best solution 后，下一次把这个 best solution 作为 initial solution 传进来。本质是一个迭代算法，不断在优化 initial solution 那段 Python 代码。

实验用的模型比较老（GPT-4、GPT-3.5、Mistral），观察到一个有意思的现象：对 GPT-4，随着 iteration 增加，meta utility 越来越大，系统在不断改善；但对较弱的 GPT-3.5 和 Mistral，随着 iteration 增加，meta utility 反而减弱，系统在迭代中性能越来越差。这和前面那个 blog 的观点一致：只有在模型能力足够好后，迭代 harness 才有效果；模型能力比较差时再迭代 harness，可能导致性能下降。论文还展示了迭代十轮后 improve algorithm 变成了什么样——从初始的简单代码，被 agent 扩展得相当复杂，结合了 exploration 和 exploitation（RL 里经典方法）、adaptive sampling、dynamic temperature 等。作者展示了 GPT-4 自己提出并实施的自我改进策略，比如 beam search、tree search、vary temperature to explore。这些其实都是 GPT-4 里已经知道的常见算法优化策略，所以它自我改进时很自然就用这些策略改进自己的 harness。这可以解释为什么弱模型在这个方法中性能会下降——弱模型可能对这些策略学得不好，而且这个框架本身要写代码，写出来的代码也可能有问题。

ADAS：agent 系统的自动化设计

再看一篇 2025 年上线的文章，标题 Automated Design of Agentic Systems，缩写 ADAS。它的重点是一个判断：一个 agent 的 harness 不光是 prompt，应该把任何跟 harness 相关的都考虑进来——novel prompts、tool use、workflows，以及前面所有的 combination。如果做自进化，应该把这所有 agent system 的部分都考虑进去。方法设计比较直接：把前面提到的 agent 系统全部由代码来定义。prompt 可以由代码表达，tool use 可以由代码表达，workflow 等等全部都可以用代码定义。��化整个 agent system，其实就是在优化这段代码——这和前面 STOP 那篇 improve algorithm 在改善一段 Python 代码本质一样。

有了这个定义后，用一个 LM 去完善这些代码，完善代码本质就是在迭代 harness。每产生新的代码、新的 harness，就有一些新的 agent，然后下游对它做 evaluation，通过 evaluation signal 继续帮助系统自我迭代。具体是：有一个 meta agent（类似优化器），目标是产生更多新的 agent。它迭代的轮数由 refine to novel and error-free 决定——meta agent 写出来的代码有时会有问题，所以用了 self-reflection，把编译错误等再给 agent，agent 据此修改。meta agent 通过写代码产生一些不一样、比较新的 agent 后，把这些 agent（也就是这些代码）加到 agent archive（类似 agent 仓库）里，里面要经过一些 evaluation，形成一个大 loop 不断迭代。

这里有些具体例子，比如 meta agent 能找到比较复杂的 agent——divide and conquer agent 会把一个 task 分解成小 task，由不同 expert 完成，最后做 ensemble 得到答案，可以理解为一个 workflow，全部由代码实现；还有 multi-step peer review agent。论文举了一个 ARC challenge 上的例子：横坐标是 iteration，纵坐标是 accuracy，这个 benchmark 相当难，初始 accuracy 连 4% 都不到，但随着 meta agent 不断迭代自己、改进 harness，accuracy 不断升高。最终得到的是一个非常复杂的 agent——先在 task 上产生五个 CoT（尝试五遍），得到五个答案后，用不同 expert 收集 feedback，根据 feedback 做 refinement 得到最终 answer，再做 ensemble。这就是在一个具体 task 上自我进化产生的一套工作流。

结果上，之前 harness 都是纯手动设计（agent 该怎么实现、什么工作流，都是人事先设定的），用 meta agent search 让 agent 系统自己在不同任务上自我迭代，性能远超过 hand design 的 agent，这个趋势相当明显。作者还把 harness 的很多部分作为 code 一起自我迭代（不只 prompt），所以也跟 prompt optimization 方法做了比较，总体来说比 prompt optimization 方法有一定提高（在某些任务上），但其他任务上提升不明显。

达尔文哥德尔机：用进化树选 parent

再看一篇 2026 年上线、和前面 ADAS 基本同一批作者的文章，提出一个叫达尔文哥德尔机（Darwin Gödel Machine）。它想改进前面 LSTM 之父提的哥德尔机。哥德尔机是一个非常抽象的数学甚至哲学层面的自迭代系统，有一个很关键的一点：系统要证明改进是有益的，才能改进。但怎么证明改进有益，在实际中很难做到。这篇 paper 的作者说，那就用达尔文的进化思想去找这种有益的改进——在自然进化中，凡是有益的改进都被环境保留下来，不好的都被去掉。这就是达尔文哥德尔机的基本思想。

这篇 paper 只做 coding agent，整体思路和前面非常类似。对 coding agent，先把它自己的代码库给它，再加上一些 self improve instruction（注意这里的 self improve instruction、也就是 prompt，是写死、固定的）。把代码库和 self improve instruction 给 coding agent，让它自己修改，改完得到一个 code diff，在对应 benchmark 上评价，看改进好不好。如果好，就保留下来，变成新的 coding agent。它和前面不一样的、也就是达尔文的部分，是用了一个树状结构去记录新的 coding agent，以及如何从新 agent 产生更多 child agent。在树上去怎么选 parent agent，是根据 agent 本身的 performance 和它 child agent 的数量。最终想达到的目的：对那些性能非常好但 underexplored（还没探索的）agent，多去探索，鼓励探索，达到 RL 里经典的 exploration 和 exploitation 的平衡——鼓励对 strong performer 的 exploitation，同时对 less-sampled 的 lineage 做 exploration。

论文给了一个进化树例子：颜色表示在 SWE-bench 上能解决多少任务，绿色解决很多（好），红色不好，最上面是最开始的 base agent。根据策略，agent 沿着进化树开始探索，平衡 exploration 和 exploitation，最终找到一个比较好的 agent。对应的性能随 iteration 增加，在 SWE-bench 上逐渐提高。

Hyperagents：meta agent 与 task agent 解耦

再来看一篇来自 Meta、2026 年三月上线的文章，叫 Hyperagents（缩写 DGMH，对前面达尔文哥德尔机 DGM 的改进）。DGM 的问题是它的设计在 coding agent 领域，自我改进和下游执行的任务是一类任务——自我改进在写代码，下游任务也在 SWE-bench 上，都是一类任务。那如果要跨领域呢？如果迭代不同的 agent——让 agent 写诗、写代码、操作机器人——由于 agent 就是自我迭代、就是它自己，一个写诗写得很好的 agent 不一定能很好地迭代自己。这就是 DGM 的问题。这篇 paper 就提出一个小改进：把 coding agent 一分为二，分成一个 task agent 和一个 meta agent。meta agent 还是去迭代自己，task agent 去执行任务。核心想法是：DGM 里这两个 agent 耦合在一起是一个 agent，泛化性能比较差，拆开成两个（meta agent 专改 agent，task agent 完成任务）后，每次自我迭代时 meta agent 可以选择改自己，也可以选改 task agent，把两个 agent 的自我进化分开，避免 DGM 强耦合带来的问题。从代码看，task agent 和 meta agent 是分别实现的两个不同 agent；paper 里作者写成一个 Hyperagent 把两个放一起，但从代码上还是分开实现，作者强行取了个概念叫 Hyperagent。

这个改动性能怎么样？左边的实验是把系统先在两类任务上做自进化——Paper Review 和 Robotics Reward Design，自进化完后再拿到数学问题上来（跨 domain）。前三类方法跨 domain 后自进化没有任何改进，只有第四类方法跨 domain 后性能有提高。第四类和第三类的唯一区别是多了 Transfer：第四类就是这篇 paper 提出的 meta agent + task agent，第三类是只有 task agent 没有 meta agent 改进。换句话说，meta agent 学的是如何改进其他 agent。如果不让它学习（不能改进自己，因为改进自己就是一个学习过程），只能改进 task agent，那就是第三类，跨领域结果很差。一旦让 meta agent 可以修改自己、学习如何 self improve，跨领域能力就起飞了。这个表强调 meta agent 对跨领域学习的泛化性非常重要。

Meta-Harness：文件系统存下所有经验

再来看一篇来自 Stanford、Chelsea Finn 的 paper。如果对 meta learning 熟悉，对这个作者应该非常熟悉，他做了很多 meta learning 工作。meta learning 和 RSI 有很多类似的地方——基本思路是有一个 model 去训练另一个 model，meta learning 里就有 inner loop 和 outer loop 的概念。Chelsea Finn 在这里又用了 outer loop 这个词，并把 harness 叫作 Meta-Harness。这篇 paper 整体思路非常简单，相当于是对前面工作的一个小的改动：在 self improve 的 loop 里，经常把新的 agent 放到一个 archive 里，archive 一般存 agent 对应的 score 或某种 agent summary。Meta-Harness 的改进是觉得 score/summary 对 agent 的信息太少了，是一种压缩。作者就说放一个文件系统（file system），存每个 agent 对应的代码、它整个所有的 reasoning trace，以及对应的 evaluation score——关于 agent 的所有信息全部以文件系统形式存下来（file system with all experience）。剩下就和前面那些 paper 很类似了：一个 agent 提交或建议一些新改动（propose harness code），有了新 harness 后再配上一个大语言模型（注意这里的大语言模型是冻结的），放到下游各项任务做 evaluation，把 evaluation 过程中产生的 reasoning trace、evaluation score 以及对应代码整个存到 file system 里。创新点就在这里。

它做了一个 ablation study：前面方法（存 score 或存 score + agent summary）和他们的方法（所有 log、所有 trace 都存下来），整体性能有很大提高。具体在 coding 相关 task 上，evaluation benchmark 是 Terminal-Bench 2，看 pass rate，两个模型——Claude Opus 4.6 和较弱的 Claude Haiku 4.5。上面都是 handcrafted harness（Claude Code 是 Claude 自家的 harness，还有 OpenHands 等），可以看到 Meta-Harness 产生的 pass rate 至少已超过原生的 Claude Code：Claude Code harness 配 Opus 4.6 只有 58% pass rate，用 Meta-Harness 后产生的新 harness 能到 76.4%；对 Haiku 4.5，原生 Claude Code 只有 27.5% pass rate，Meta-Harness 能产生 37.6%。作者还给了一个自进化 harness 的例子：在 Terminal-Bench 2 上，Meta-Harness agent 自己发现经常解这一类问题时要做 environment bootstrapping（agent 开始一个任务后要先读整个代码库、看环境缺什么包，需要很多次工具调用）。它做的一个改动叫 Hypothesis：直接预先产生一个 environment 的 snapshot，在第一次 LM 调用之前把这个 snapshot 直接放进 LM 的 prompt 里。好处是避免 agent 在任务刚开始时花三到五次去探索环境，通过预先给 LM 提供环境信息，让 LM 更快更好地解决任务。

AHE：把可观察性引入 harness 工程

再看一篇 2026 年上线、来自复旦和北京大学的文章，叫 Agentic Harness Engineering（AHE），对前面 Meta-Harness 的思想进一步改进。前面提到可以用文件系统存复杂的自我迭代各种 log，但最开始也提到 agent 系统其实挺复杂的，有不同部分。那 agent 怎么知道具体应该修改哪个部分？这篇 paper 就把人类比较好的工程实践里的一个概念引入进来——observability（可观察性）。总共引入三种可观察性：component observability（把 agent 系统人为分成很多部分，比如 system prompt、skills、tools、middleware（理解为常说的 hook）、sub agent 的 configuration 以及 memory，人为划分的意思是让 agent 修改时必须明确说明要修改哪一个部分）、experience observability（agent 执行过程中产生的各种 log，改进在于 log 可能很长、比如十 million token，用了一个 Agent Debugger 把 raw trace 写一个分析报告，压缩成 10K tokens）、decision observability（agent 在修改之前必须写一个 Manifest，先说想改哪个 Component、为什么这么改，相当于提前做预测并给出理由；根据 Manifest 进到下一轮修改后，就能看到上一轮预测的修改哪些真起效了、哪些没起效，这个结果可以存起来作为 agent 下一次迭代所利用的信息）。

举一个图：Iteration One 之后，Manifest 里记录两个 agent 想做的改动——Change One（level 是 prompt，即对 prompt 做改动）、Change Two（level 是 tool，即对 shell tool 做改动），Manifest 记录哪些文件被修改、做了什么修改，会有一个 predict fix，这个 Manifest 进到下一轮迭代。下一轮 agent 在具体的 task 上 evaluate，就知道它 predict 的到底对还是不对。如果发现改动有效就接受，无效就 rollback。更进一步，每一步的 Manifest 里，agent 可以预测这个改动会 fix 这个问题，还是会导致 regression。经过下面迭代时，因为可以验证改动到底是 fix 还是 regression，相当于有了 ground truth。有了 ground truth，prediction 就可以算 precision 和 recall：agent 预测 fix 时，precision 和 recall 分别是 33.7% 和 51.4%，好于 random baseline；预测 regression 时，precision 和 recall 分别是 11.8% 和 11.1%。这个结果翻译成对 agent 系统的理解：因为对 fix 的预测整体好于对 regression 的预测，说明 agent 能知道自己这个修改能不能解决这个 bug，但它不知道自己的修改会不会引入新的问题。这跟平时用 AI 编程工具的体感一致——经常让 AI 修 bug，它能很快修好，但又会引入新 bug。这也是下面一个值得研究和改进的。

整体结果比较也在 Terminal-Bench 2 上。上面是 human designed harness（OpenCode、Codex——作者估计因为在国内用不了 Claude Code，所以比较的是 Codex），下面是一些自进化方法，NexAU 零是起始 harness，AHE 是这篇 paper 的方法。可以看到 AHE 结果好于 Codex。一个有意思的 ablation study：从 baseline harness 进化到 AHE Full harness，把进化完成后的改动分 component，原样一个一个加回去，看提升到底来自哪里。如果把 AHE Full 里关于 Memory 的改动加回去，改善最大；其次是 Tool，然后是 Middleware——可以看出对现在 agent 系统的改进，从 Memory 和 Tool 角度最有效。比较有意思的是，如果把 System Prompt 的改动加回去，结果反而变差（baseline 是 69.7%，加了 System Prompt 改动后变成 67.4%）。可能解释是 System Prompt 的改动可能要跟其他改动结合，单独把 System Prompt 改动加回去、缺少其他改动，性能可能下降。

HarnessX：九个维度的乐高式自进化

再来看一篇来自 Darwin Agent Team（小米旗下专门做 agent 的团队）的文章，提出 HarnessX。基本思想比较直接，跟前面那些工作非常类似，比较不一样的地方是 Compose：把 agent harness 自进化过程定义成九个维度，让 agent 自动地从这九个维度里迭代进化，有点像乐高积木——人为先把整个 agent 系统切成九个不同维度，后面进化时这九个维度都是独立的，可以让 agent 系统自动插拔：哪个维度不好就把那个维度替换掉。九个维度分别是 Model（harness 里用什么模型）、Context、Memory、Tools、Sandbox、Evaluation、Control、Observe、Train。这些维度已被事先定义好。开始自进化时，用一种 Config 的形式决定每个维度、每个 component 用什么，给 task agent 做 evaluation，产生各种 log（trace）。trace 给到下面的 Evolve Agent，把它又分四个步骤（整体叫 AEGIS）：Digester（trace 有很多信息、比如十 million token，digester 去总结前面 trace 里重要信息，跟前面 agent debugger 类似）、Planner（类似预测应该做哪些改动）、Evolver（做具体的 smoke test）、Critic（评价改动到底好不好）。最终产生的结果又进到下一轮循环。这部分基本和前面非常类似，不太一样的是 HarnessX 把整个自进化系统人为分成九个不同积木，搭积木、替换积木式地迭代。

这篇 paper 还提了一个更大胆的想法：harness model co evolution loop，不光要迭代 agent harness，还要迭代 agent model 本身，用 GRPO 去迭代模型。一个实际例子：在 GAIA benchmark 上使用 Sonnet 4.6，第十轮时成功率从 77.7% 掉到 74.8%。digester 开始分析前面一轮的 trace，发现一个 failure pattern——去 Wikipedia 取信息时返回的都是空字符，主要是 Web Search 工具有问题。planner 收到 digester 总结后制定两个目标，evolver 提出三个改进建议：提出一个新工具叫 Wiki Text Fetch、改一下 prompt、改一下 config 把新的 Wiki Text Fetch 注册进去。critic 进来检查，同意了这个方案，同时 reject 掉另一个方案。经过改动后，GAIA 的 pass rate 从 74.8 增加到 79.6。

四、收益归因：过拟合、test-time scaling 与真进步

前面讲了大量 harness evolution 工作，结果都相当不错，都说自己涨点、能泛化。那是否真是这样？来看一篇来自 Amazon 和 NPU、这个月刚上线的 paper。它主要想讨论：前面讨论的很多 harness evolution 工作，所谓的 gain 到底来自什么地方？它对这个 gain 做了 dissect，研究 harness 的 gain attribution 在哪里。结果非常有意思：它把 harness gain 的 attribution 分成三部分。第一种是 overfitting——agent 在自进化 harness 时，其实是 overfit 到具体的 benchmark 上去了。第二种是 test time scaling——很多 harness 自进化框架会做 majority voting 之类，需要消耗更多 token，消耗更多 token 本质上就是在做 test time scaling（这很容易理解，用 Claude 或 Codex 把 thinking level 打高一点，结果自然好一点，所以 test time scaling 并非 harness 自进化带来的）。第三个才是真正想要的 generalizable improvement。作者发现，好多 harness 自进化框架的改进，很多来自 overfitting，还有来自 test time scaling。这个结果展示了：之前很多工作并不是想象中那样有效的 harness 自进化框架。

那如何评价这三种 attribution 各占多少？作者的方法：有一个 base harness，有一个 harness 自进化框架得到的 evolved harness，前序 paper 观察到的 gain 就是这两个 harness performance 之间的差值。问题是把这个 gain 差值拆开。先衡量 gain 里多少来自 test time scaling：如果知道 evolved harness 用了多少 token（比如 majority voting 导致 token 数量增加），就把 base harness 的 token budget 也提高，让它用和 evolved harness 类似的 token budget 重新跑一遍 task，性能自然会增加，得到的性能记作 h scale，算出 test time scaling 带来的性能提高（简写 T）。再衡量 overfitting：作者观察到 evolved harness 里有一些 agent、一些 hard code、钻空子的地方，就用另一个 agent 去看 evolved harness 的代码，把 hard code 或钻空子的地方全部找出来（后面看具体例子），把潜在 overfitting 的地方去掉，evolved harness 性能肯定会下降，下降的部分就是 overfitting 的贡献。对 test time scaling 是做加法，对 overfitting 是做减法，两部分贡献能测出来后，剩下的性能就是 generalizable improvement。整体思想：观察到的 gain 减去 T 和 O，剩下的就是 G。

具体 test time scaling 的计算用了 compute matching 的方法：如果 H hat（进化出来的 harness）相较于 base harness H zero 用了十倍的 LM call，就让 base harness 也有十倍的 compute budget，用 majority voting 方法利用这十倍的 compute budget，使 base harness 和 evolved harness 的 compute 一样，再算加了更多 compute budget 后 harness 的性能与原始 base harness 性能之间的差，作为 test time scaling 的衡量。

衡量 overfitting 更复杂一些。作者观察到现在的 harness 进化框架有两个问题：第一，agent 会自己发现 direct shortcuts（捷径），包括用固定答案、硬编码的查询 table，或字符匹配规则，这种做法甚至不需要 LM——harness 进化后把最核心的大语言模型丢掉，直接进化成规则引擎；第二，它会发现和 benchmark 相关的漏洞然后直接使用。

一个 overfitting 例子来自 Meta-Harness，在 ALFWorld benchmark 上，用的模型是千问 3.5 的 0.8B（一个非常小的模型）。ALFWorld 本身是通过文字评价模型和真实世界交互的能力（真实世界以文字形式表述，比如告诉 agent 在房间里有很多 shelf、drawer，task 是把花瓶放到保险箱里，agent 需要跟文字环境互动，理解环境、做出 action，最后把花瓶放进保险箱）。但在这个自进化 harness 框架里，agent 发现了一些潜在规律——物品和 location 有强相关性，于是自己就在 harness 代码里硬编码了一个 lookup table（location priors）：知道 mug（水杯）一般在 coffee machine、counter table 这些地方；又把 task 或要执行的 action 硬编码了，比如 task 要求加热就直接用 microwave，要冷却就直接用 fridge，甚至把 benchmark 里已存在的物品都事先硬编码好。后果是 agent 不需要再跟环境做太多互动，最终即使一个非常小的 0.8B 模型，经过 harness 自进化框架后在这个 benchmark 上也能达到 100% 准确率——当然这 100% 全是硬编码 overfitting 引起的。更极端的是，代码最后变成一个 503 行的文件，整个 harness 甚至把 LM call 整个去掉了，变成纯纯的规则引擎，甚至不需要大语言模型了。进化到最后，Meta-Harness 已经把它最核心的 LM 扔掉了，完全 overfit 到了 ALFWorld 上。论文还提到，即使用一个 held out 数据集帮助避免 overfitting 也没有用——因为 held-out 如果还来自 ALFWorld，这些硬编码还是起作用，还是 overfitting。

另一个 overfitting 例子来自 LiveMath benchmark，几个不同的 harness evolution 框架都有 overfitting 问题（Meta-Harness、AHE、SkillOpt）。这个 benchmark 数据集里经常出现一个选项："One of the remaining options is correct, stronger result can be proven"，意思是数据集设计这个选项是想把问题变难——选项里有一个对的，但在这个正确选项的基础上，因为这个 benchmark 很多是证明题，还有一些更强的结论，所以故意设计了这样的选项。带来的问题就像平时应试教育——遇到一个长的选项，总是选那个长的就对了，不管你是否理解它的意思。所以这个 harness evolution 框架发现只要出现这种选项，直接选它就好了，基本每次选这个答案都是对的。另外两个自进化框架甚至给出了原因，比如「只要出现这个选项，它就是一个 first-class 的 candidate，每次都要选它，choose it」。这是一个典型的 overfitting 例子。

直接看结果：这个表格测量了 Meta-Harness、SkillOpt 和 AHE 几个主流 harness evolution 框架，一列是不同数据集和不同大语言模型，O 是 overfitting、T 是 test time scaling、G 是 generalizable improvement，希望 G 这列越大越好。Meta-Harness 在 ALFWorld 和 LiveMath 上基本全是 overfitting，在 CREATE 上基本都是 test time scaling，只在 SWE-bench 上 generalizable improvement 稍微好一点。SkillOpt 也观察到大量 overfitting，AHE 也类似，大量 overfitting 和 test time scaling。这个工作挺有意思——大家都在疯狂卷 harness evolution 框架时，这些作者能从另一个角度去审视这些工作有多少是真正 solid 的。这篇 paper 至少从某种程度上说明：Meta-Harness、AHE 虽然提出的科研想法是好的，但对实际效果来看，很多其实并不是来自 general improvement。

五、RRSI：加正则化的递归自我改进

再看最近 Google 刚上线的这篇文章，叫 RRSI，对前面那篇 Amazon + NPU 的 paper 做回应或改进。前面提到现在很多 harness evolution 框架其实是 overfitting 或 test time scaling，这篇 paper 提出的观点就是：要不我们在 harness 自进化过程中加一个 regularization（第一个 R 的意思），目的是避免前面提到的那些 overfitting，从而得到核心想法：regularized recursive self-improvement。

先说对这篇 paper 的整体感觉：虽然来自 Google，但它找的问题是对的（解决 overfitting），不过解法非常 engineer——加了很多类似人类先验或人类规则的方法去减少 overfitting。本身加这些很复杂的规则，就是在 overfitting 这个具体问题。所以对这个解法到底是不是最优，有点怀疑，可以抱着批判的思路看它到底提出了哪些 regularization。它把 regularization 分成两部分：proposal side regularization 和 selection side regularization。

proposal side：做了一个叫 L0 style annealed update sparsity 的东西，说得挺复杂，本质是 harness evolution 框架里在 propose 改什么时给它一个限制（update capacity），随着修改轮数增加，可以改的地方应该越来越少（update budget decreases over time）。后果是自进化过程中，刚开始时 proposer 可以做 broader edits（很广泛的修改），进入比较后期的自进化轮数时，修改就不能太多，后期倾向于做 sparse 的修改。B 的限制是修改时要能看到整个 history——在这个阶段要知道前面哪些轮的修改有帮助、哪些没帮助，主要是不只看最近有帮助的修改，而是看整个历史记录。C 的作用是当尝试了很多次都没有进展时，强制 agent 去看一个新的不一样的方向。B 和 C 其实就是在强制 agent 跳出 local optimal，尽量找 global optimal。

selection side：整体这些 regularization 其实是为了避免选一些高分低能的 harness——在某些 benchmark 上得分很高，但由于各种原因泛化能力很差。第一个 leakage screening 专门针对前面提到的 overfitting 例子，看 harness 进化过程中有没有出现 benchmark specific 或 task specific 的 logic，比如有没有硬编码像 ALFWorld 那些 location prior 之类的东西。第二个 noise adjusted performance floor，也是为了避免高分低能——有时在某些 benchmark 上得分很高，但可能是噪声造成的，F 给了它一个 budget constraint，如果修改非常复杂，这个复杂度是否有必要。最后一个类似，做 structure pruning，如果有一些部分没什么作用，这些部分应该被剪掉、去掉。可以看到这些 regularization 非常 ad hoc、非常人类的手工设计，跟机器学习统计里提出的 regularization（如 lasso、L1 或 L0）不一样，后者的正则化非常简洁、elegant。这也是觉得这篇 paper 解决的问题对、但提出的方法不一定最优的原因。

Google 这篇文章的结果主要比较 in distribution 和 out of distribution。in distribution 用 Harvey（法律数据集），out of distribution 用 JobBench、APEX-Agents。在 in distribution 数据集上，RRSI 整体性能和之前的方法（Meta-Harness、AHE、HarnessX 等）其实不相上下、差不多，甚至更差一些。比较好一点的是在 out of distribution benchmark 上，RRSI 性能有所提升，说明泛化性能会好一点。但整体这个提升点数不是特别明显，当然有一定涨点，不过这种变化也不一定完全是方法本身造成的。从结果也许可以看出：光从 harness 本身进化，可能远远不够，也许 LLM 本身的进化也是需要的，所以像 HarnessX 提出的共进化也许是下一个趋势。

总的来说不太喜欢 Google 这篇工作。本身 harness 的自进化要解决的是之前的 harness 都是 hand design（手动设计）的问题，Meta-Harness 等就是想避免 hand design 的问题；Google 的 RRSI 又相当于开了历史的倒车，引入很多 hand design 的方式去实现 regularization。从整个研究思路来说，问题本身值得解决，但通过加 hand design 的 regularization 方式，不是一个很好的方法。

六、open-endedness：解决过拟合的根本出路

前面已经捋了很多 RSI 文章，按现在研究趋势，最大的问题是过拟合。过拟合本质是什么？就是用固定的 benchmark 去评价 RSI 系统，导致 agent 实现了 reward hacking。补充一篇 2024 年上线、作者全部来自 Google DeepMind 的文章来收个尾，也掺杂一些个人看法。这篇文章主要想讨论的观点是：对 Artificial Superhuman Intelligence，如果要实现，可能需要这种 open-endedness。个人认为 open-endedness 其实就是解决前面提到的用各种固定、人设定的 benchmark 去 evaluate RSI 系统。

什么是 open-endedness？打个比方，现在的 evaluation 或 benchmark 有点类似打游戏，游戏有很多关卡，总会有一关最后被打穿——这个游戏没有更多的关卡。如果 agent 系统足够强大并不断尝试，终有一天会把这个游戏打穿，也就是 overfit 到这些 benchmark 上。另一个比方是考试，满分一百分，考到一百分后不断尝试，可能某一天达到一百分，后面就没有值得尝试的东西了。所以 open-endedness 是说，也许不应该用固定的 benchmark 去评价 RSI 系统。如果真的想要超级智能，它也许需要两个特点：Novelty（新颖） 和 Learnability（可学习性）。对于数学问题，人类会不断创造新的数学问题，这些数学问题对人来说都非常新颖，而且人类在解决、证明这些数学问题时能学到经验，这就是可学习性。文章把 novelty 和 learnability 跟 observer 联系起来：如果一个系统能产生一些 artifact（螺旋桨飞机、喷气飞机、宇宙飞船），这些 artifact 对不同 observer 的 novelty 和 learnability 不一样——螺旋桨飞机对老鼠来说没见过（很 novel），但老鼠不可学习；喷气飞机对人很新（没见过）且可学习；宇宙飞船对外星人不 novel（外星人科技发达，见过很多宇宙飞船），但存在一些可学习的东西（里面可能有值得学习和借鉴的）。换到 RSI、agent 系统也是类似的：需要系统不断找到新问题，并在解决新问题的过程中从中学习。为了进化 AI 系统，首先要有 open-ended 系统帮助 AI 进化，或者 AI 有 open-ended 特性，这样避免像考试有满分、打关总有打穿的一天——因为对这两个特性来说，你永远都是无止境的，从而避免 overfit 到某个具体 benchmark。

这篇 paper 也提了一个具体的 open-ended system 最后怎么演化。作者认为 AI 系统应该跟人共同进化：首先 AI 系统能 self-improve 并且 automatically（自动发现一些问题，也就是前面说的 novelty 和 learnability）。但当 AI 系统发现新知识后，这些知识要能被人理解、教会给人，人会消化这些知识，消化后反馈给 AI 系统，提供一些 control、guidance 或 oversight，然后不断迭代。AI 和人如果看作整体，他们又会产生更多 open-ended artifacts。总的来说是一种人机协作方式，从而达到最终的 ASI。这是一种比较理想的情况——人类真正参与到 AI 的进化中，提供协助和监督，而不是 AI 像现在看到的在一个封闭体系里不断迭代。

七、工业界的信号：When AI Builds Itself

前面看了很多 research paper，现在换个方向看工业界进展，以 Anthropic 的 blog 为代表，标题叫 When AI Builds Itself（当 AI 能够创造自己）。它在这个地方给出了一个时间线：AI 从 Chatbot 变成 Coding Agents 到现在的 Autonomous Agents。注意这里的 Autonomous Agents，Anthropic 在这个 blog 里画的是人是需要发号施令的——人需要设计去解决什么问题，只不过把问题定义好后给 Chatbot 或 Agent，Agent 自己能调用其他 Agent 把问题解决。所以现阶段人还在定义问题，AI 只是在执行。类似的，最近很多数学问题都已经被 AI 解决了，但这些数学问题本身还是人定义的。真正想达到的是一个闭环的 loop，在这个 loop 里没有人的——AI 自己解决问题，同时 AI 自己定义问题。这其实也是前面 DeepMind 那篇观点文章提出的 novelty、learnability——也是在说 AI 要有一个自己定义问题的能力、自己去发现新知识的能力。当 AI 有了这种能力，就可以自己训练自己，知道自己怎么改进自己、该改什么地方。

Anthropic 在这篇 blog 里放了一个图，横坐标是时间（从 2025 年 9 月到 2026 年 9 月），纵坐标是 Claude Code 的 successful rate，是一些不同的模型——从较差的 Claude Sonnet 4.5 一直到 Claude Fable 或 Mythos 5.1（录视频时 Opus 5.5 也已经出来了，所以还不是最新的）。Anthropic 把任务分成几类：从比较简单的 trivial task 一直到比较困难的 open-ended task。从早期这些模型解决得并不是很好，可以看到 open-ended problem 的 successful rate 一路飙升，到最新的 Mythos 5.1，successful rate 已经能到接近 90%——意思是即使对这些很难的问题，现在最强的模型也基本能够解决。这里不要只看绝对值，要看这个上升的斜率，这个速度非常惊人。如果按这个速度接着发展，也许不需要一年，AI 解决问题的能力就非常强。

但这里又回到 DeepMind 那篇观点文章：这只是代表 Claude Code 解决问题的能力很强，但这类 AI 是否有定义问题的能力，还不一定。就像人类数学家一样，很擅长证明某个已经预设好的数学问题是一种能力，但寻找哪些数学问题值得研究、值得证明，是另一种能力。讨论 RSI 时，这两种能力都很重要，AI 也许欠缺的是第二种。

Anthropic 在这篇文章里对未来做了展望，提出三种情景。第一种：AI 发展的能力由于某种限制（电力、芯片等）放缓，但 Anthropic 认为这种情景不太可能。第二种：AI 的发展能在很大程度上被自动化，但人类还是发挥了重要作用——人类来设定研究方向、判断结果好坏。Anthropic 认为这是将来最可能发生的情景，跟 DeepMind 那篇观点文章最后的图一致——人和 AI 共同进化，但人在某种程度上起到主导，人判断方向、判断结果好坏，只是中间执行的过程全部用 AI 自动化。第三种：现在所谓的 RSI——AI 能完全自动化地迭代自己，开始建造下一代。Anthropic 在这一段说他们不太确定这是否可能发生，有很多不确定性。

八、回到 Hinton、Bengio 的那篇论文

前面介绍了很多领域进展，现在回到视频开始提到的那篇 Hinton、Bengio 等大佬最近刚上线的文章。标题其实提了一个问题：如果按 Anthropic 这样的公司用 Claude 自己迭代自己的方式，会不会导致智能爆炸？直接跳到正文。这些作者认为现在已经有一些 preliminary evidence，表明 software-driven intelligence explosion is possible——软件领域通过软件驱使的智能爆炸是可能的。这跟前面看的 Claude Code session success rate 趋势图一样：如果按这个趋势，Claude Code 继续迭代自己，这种 intelligence explosion 有可能达到。作者认为这种智能爆炸会有两个部分或特点：当 AI 系统自己越来越强时，它会把这个对自己的研究变得更高效。这里用一个词叫 workforce（姑且翻译成一种能力），这种能力又产生更多、更好的 AI 系统，从而继续扩大能力，形成一种 recursive feedback loop（递归反馈回路）。虽然现在的证据表明这种能力还非常原始，甚至有一些不太好的地方，但它表明自我迭代机制可以极大加快 AI 的发展进程。所以在这些大佬眼里，这个 RSI 是极有可能导致智能爆炸的。

重点提一下这篇文章谈到的 social impacts——如果真的实现智能爆炸，对社会会有什么影响。作者列举了几个：第一个，整个社会可能无法驾驭或适应这种 AI 带来的能力。举例：网络攻击、生物安全、劳动力市场。原因是技术发展太快，社会还没有时间去适应。一个事情往往有两面：如果 AI 发展太快，网络安全是一个问题，但对网络安全的防范可能还跟不上。另一个两面是 AI 既可以被用来制造病毒，也可以被用来制造疫苗——病毒扩散很快，但疫苗需要生产，所以 AI 快速发展可能造成这种一体两面的 mismatch：攻的一面发展很快，防的一面可能跟不上。

第二个，人类会逐渐失去对 AI 的监管，因为已经把 AI 发展自动化了，人类在 AI 发展过程中比较少参与。而且现在的 AI 系统让人类非常难以监管，甚至有时如果 AI 系统没有被很好对齐，它有可能对自己的下一代进行投毒，或绕过某些安全措施。举例：OpenAI 攻击 Hugging Face 可能还是一个比较小的事故，后面有没有可能发生更多非常严重的事故？会不会导致人类灭绝（extinction of humanity）？

最后一个比较有意思，原文叫 Erosion of checks on power——政府、公司、国家之间的 power 其实有一些平衡，AI 快速发展可能导致这种平衡失效。比如用 AI 进行网络攻击，一个很可能军事能力一般的地区或国家，通过智能爆炸就能对别的国家造成很大危害，又会造成对手采取升级防范（使用更强大的 AI），这种 power 失衡可能造成局势动荡。文章最后还给了对一些 policymaker 如何提早防范前面可能出现问题的建议，这里不再展开。

读完这篇文章后的个人观点：智能爆炸短期内完全是有可能的。我们作为社会的个体，或多或少应该开始思考——在这个 AI 快速发展、智能爆炸真的来的那一天，我们是否做好了准备，能快速适应智能爆炸带来的冲击？至少现在要开始思考这些问题。用这篇文章的一句話结尾：虽然智能爆炸还有一些不确定性，但用这种 AI 自己迭代自己的方式，可能迟早会导致智能爆炸，而我们现在还没有准备好，所以要提早准备。当智能爆炸开始时再准备，可能就太晚了。用文章原话说，就是 the window for action may close（采取行动的窗口可能已经关闭）。

彩蛋：如何追踪这些 paper

视频最后分享了一个找 paper 的方法。找 paper 基本根据目的，一般有两种目的。第一种是想快速跟进领域进展，这类 paper 只需快速阅读，知道每天有哪些新的 idea 就够了，不会仔细看实验结果，大概了解大家都在研究什么即可。这种略读的作者自己做了一个 app 叫 AIDaily.win，主要去网上爬信息、一小段话（因为看中文比较快所以做成中文的），除了 paper 还有 AI 新闻，每天扫一眼知道大家都在做什么。不一定要用这个 app，现在 paper 追踪或新闻追踪工具特别多，甚至直接用 ChatGPT 做一个定时任务就可以，找一个自己顺手的就好。

第二种是非常仔细地把领域脉络捋清，这时需要知道每篇 paper 之间的关系，有些具体 paper 会非常仔细看。对这类，用得最多的是看 paper 的 citation——这篇 paper cite 了哪些 paper，以及哪些 paper cite 了这篇 paper。用得最多的是 Google Scholar。举个例子，TTRL 这篇，想知道它和相关 paper，会往后看（后面发表哪些 paper cite 了它），用 Google Scholar 点 Cited by，这是所有 cite 这篇 TTRL paper 的 paper，Google Scholar 自动按 citation rank，放最前面的就是 citation 最多的，浏览一遍就知道后面有哪些 paper cite 了它。往前看就是看这篇 paper 本身 cite 了哪些 paper，一般一篇 paper 都有 background 或 related work，比如 TTRL 在 related work 里 cite 了好多之前的 paper，也会往前看。一般会优先往后看，因为往后看时后面的 paper 会对前面的 paper 做总结，提到前面这些 paper 有哪些优缺点，优先看后面的 paper，通过后面 paper 的 related work 对前面工作总结，大概对前面工作做一个快速理解，建立 high level picture，然后再往前看那些比较老的 paper。这是找 paper 的两大方式。
