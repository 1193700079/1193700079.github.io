一台 8 卡 RTX PRO 6000 的推理机，nvidia-smi 显示每张卡 97% 利用率，看起来已经被榨干了。但同一时刻功耗只有 170W，离 600W 上限还有三倍余量，显存池 93GiB 里只躺着 2% 的 KV。这台机器到底满没满？这篇文章把一次真实的 10 分钟监控窗口拆开讲：利用率为什么是个谎言、监控数据怎么被日志噪音骗、TTFT/TPOT 分别量的是什么、32 路并发能对应多少用户、以及 SGLang HiCache 的单机能力与跨机分布式能力的边界。

利用率是个谎言

nvidia-smi 的 utilization.gpu 指标有个著名的坑：它统计的是「采样窗口内 GPU 有任何一个 kernel 在跑的时间占比」，而不是算力占用率。一条 50k+ token 的长 decode 流，每步 kernel 很轻，但步数密、持续不断，就把这个「时间占比」顶到了 97%——而实际功率只有 170W，算力余量三倍。

真正能区分「假满」和「真满」的是三个数：

  • power.draw 相对 power.limit。170W/600W 说明算力还有很大空间；逼近 limit 才是带宽或功耗撞墙。
  • running-req / queue-req。SGLang 日志每步 decode batch 都打一行，单条 50k context 的请求 running-req=1、queue-req=0，说明根本没有并发。
  • KV token 使用率。full token usage 0.02 意味着 93GiB 显存池只用了 2%，长 context 也才 50k token。

结论是：utilization 97% 只是「有 kernel 在跑」，不是「机器满了」。判断推理机是否榨干，要看功率逼近 limit、KV 池逼近打满、并发逼近 max-running-requests 这三件事同时发生。

十分钟监控窗口的坑

挂了个 30 秒采样一次的监控，直接踩了两个坑：

  • 日志被 404 探针刷屏。上游有个监控系统每几秒打一次 /metrics 端点，而 SGLang 启动参数里没开 --enable-metrics，于是每条都是 404 Not Found。十分钟里刷出四万多条 404，把真正的 batch 行顶出日志 tail，监控脚本 grep 不到 batch 行就静默，误判成「没有请求」。
  • 30 秒采样撞上波间空隙。请求是突发型的：一波请求打上来，功率冲到 2200W，请求跑完，功率跌回 900W 的空闲底噪。30 秒采样间隔正好卡在波间空隙里，采到的永远是 running-req=0，而残留的吞吐行是上一波请求的最后一条 batch 行，不是当前状态。

这两个坑叠加，让监控看起来「没变化」，实际上机器一直在干活。正确的做法是：统计整个窗口的 batch 行分布（并发数直方图、功率峰值、KV 使用率），而不是采样瞬时值。瞬时值适合告警，分布才适合判断负载形态。

TTFT / TPOT 的口径

推理侧有两个最核心的延迟指标，口径要分清：

指标度量和负载的关系
TTFT（Time To First Token）请求发出 → 首 token 返回，即 prefill 耗时和并发压力关系弱（KV cache 命中能压下去），但排队时会暴涨
TPOT（Time Per Output Token）首 token 后每个 token 的间隔，即 decode 单流延迟随并发线性变差，是判断「带宽撞墙」最早的信号

拿 TTFT 判断「机器有没有被打满」会误判：prefill 是计算密集，KV cache 命中时 TTFT 可以很漂亮，但 decode 带宽可能已经饱和。该看的是 TPOT 的分布——TPOT 开始上涨，就是并发逼近带宽极限的前兆。反过来，TPOT 平稳（几个毫秒级）说明 decode 不抖，机器还有余量。

三十二并发能撑多少用户

max-running-requests 32 不是「32 个用户」，是同时最多 32 条请求在解码，超出的进 queue-req 排队。换算成用户数要代入占用率公式：

单用户占用率约 0.2 条流。32 路 ÷ 0.2 ≈ 150–160 个活跃 agent 会话。但真正的天花板不是 32 这个数字，是 GPU 带宽：长 decode 是 memory-bandwidth-bound，并发翻倍后单流吞吐掉一半，实测大概 10–20 路就把带宽打满，32 路是理论上限、实际先撞延迟墙。KV 池不是瓶颈，50k 请求 × 32 路对 1M 池只用了零头。

实际可用的答案：稳态扛住、延迟可接受是 10–20 个并发 agent 会话（约 50–100 个真实用户，考虑人在读、工具在跑的空闲时间）；32 路并发能排进去但单流延迟翻倍；超过后请求排队，queue-req 开始涨，这是该看的告警指标。

动态扩缩容的节点

「人少时 token 速率极快、人多时用满」这个目标，调度层其实已经做到了——SGLang 的 continuous batching 就是这个机制：人少时单流吃满全部带宽（单流吞吐就是这台机的理论上限），人多时自动 batch 拉聚合吞吐。这不是要开发的功能，是已经拿到的。

GPU 层真正的动态扩缩容，工业界现状分几档：

方案成熟度说明
DP 副本 + 队列深度扩缩（sglang-router / K8s + Karpenter）生产可用多副本同模型，队列深了加副本、队列空了杀
Serverless GPU 平台（Modal / RunPod / Baseten）生产可用人少时 GPU 直接释放，按秒计费，代价是冷启动 30–60s
PD 分离（prefill/decode 拆到不同机器）SGLang 已支持decode 机专职吐 token，长 context 场景 TTFT 和 TPOT 都优化
动态 TP（运行时改 tp-size）研究阶段FlexTP/DMT 论文有，SGLang/vLLM 的 tp-size 启动时固定，改就要重启
MIG 切卡本机不支持RTX PRO 6000 是工作站系，没有 MIG（只有 A100/H100/B200 数据中心卡有）

8 卡单机上，「人少时少用卡」做不到（没有 MIG、TP 改不了、权重常驻底噪 ~120W/卡 降不下去）。真正能落的是队列深度驱动的横向扩缩：加 --enable-metrics 让 Prometheus 能读到 sglang:num_queue_reqs，写一个 scaler——队列持续 >0 超过 N 分钟就起一台同配置机器挂进 fallback 代理的上游列表，队列持续为 0 就关它。fallback 代理本身已经是个多后端路由，天然就是负载均衡器，加后端只需改一行环境变量。

但先泼个冷水：当前负载平均 1–2 路、峰值 5 路，连舒适区（12–16 路）的零头都没到。这种负载下做动态扩缩，大部分时间 scaler 都会判「人少」，省下的电是第二台机器的电费——而第二台机器现在根本不存在。真正的问题不是撑不住，是那台机 95% 时间在空转烧 ~900W。解法是降配（tp=4）或者喂更多并发，而不是扩缩容。

HiCache 的解路

SGLang 的 HiCache 是分层 KV cache：GPU 显存一级 + 主机内存二级。本机开的是单机版 HiCache——128GiB 主机内存二级缓存，write_through 写穿策略。实际效果：agent 会话重复的 system prompt + 历史前缀，第二次直接命中 host 层，TTFT 省掉整段 prefill。对 50k+ context 的长请求这是真在起作用的，日志里 full token usage 0.02 但请求秒回，一部分就是它。

文章标题里说的跨并行分布式四件套——CP 页分片、PP 缓存同步、统一 KV 布局、P/D 复用——本机一个都没上：

特性需要的条件本机现状
CP 页分片--cp-size > 1（context parallel 多实例共享 KV）cp=1，单实例
PP 缓存同步--pp-size > 1 + 跨阶段缓存对齐pp=1
P/D 复用--disaggregation-mode + 独立的 prefill 池/decode 池没有分离，单池
统一 KV 布局多节点间用 Mooncake 之类的传输引擎共享前缀单节点，无跨机传输

那套东西是给「多节点 PD 分离 + 多副本共享同一份前缀缓存」的场景做的——prefill 节点和 decode 节点分开部署，请求在两个池之间带着 KV 迁移，靠统一布局避免重复计算。单机 tp=8、单池的形态下，HiCache 的 host 层已经把前缀复用最值钱的那部分（本机内）吃掉了。跨机 KV 共享的价值要等真做出「10 台机器 + PD 分离」时才显现，而那正是动态扩缩容的前提。

结论与下一步

这台 8 卡 PRO 6000 推理机的实测画像：utilization 97% 是「有 kernel 在跑」，不是「机器满了」；真正的负载是突发型的单条长请求，平均并发 1–2 路，功率在 900W 空闲底噪和 2200W 请求峰之间振荡；KV 池只用了零头，显存和功率都有大量余量。监控链路里，--enable-metrics 没开，上游 Prometheus 探针打了一万多次 404；nInfer 备池全挂，fallback 链实际只有 SGLang 单机扛。

要榨干或者省电，三个动作按优先级排：

  • 加 --enable-metrics。零风险（不改推理行为），让 Prometheus 能读到 num_queue_reqs、token_usage、time_to_first_token_seconds、e2e_request_latency_seconds，设备侧指标和请求侧的 TTFT/TPOT 合起来才是全图。
  • 修 nInfer 备池。fallback 链是断的，SGLang 一挂直接全停，这是比「榨不榨干」更紧迫的可用性风险。
  • 降配或喂并发。tp=8 对一个 27B 模型在平均 1–2 路并发下明显过度配置，tp=4 单流延迟几乎不变、省一半电；要拉满则把客户端并发顶到 16–32 路，让 TPOT 开始上涨、功率逼近 4800W 上限。

动态扩缩容和 HiCache 跨机分布式，都是「先有足够请求量、再有横向多节点」之后的事。先回答请求量增长曲线，再决定扩缩容还是降配。
