这篇论文叫 《You don’t need long context》（arXiv 2611.05306，2026-11-03），作者群来自 NVIDIA 研究院，挂在「Project Moonshot: Local Frontier Intelligence」下。它一句话就能概括：前沿语言模型在做长程任务时，把上下文压到 16K–50K，任务准确率几乎不丢，而生成成本能砍到 1/3 到 1/7。这篇把它当成技术阅读精读，把三个研究问题、三种上下文管理策略，和成本曲线一次讲清。

一、为什么长上下文这么贵

根子在于自回归生成的深度成本：生成第 d 个 token 时，attention 要把之前所有 token 的 KV 都读一遍，成本随深度近似线性增长。KV cache 的显存占用也是线性涨的。所以输入越长，后面每个输出 token 生成得越慢、越贵、越吃显存。

论文 Figure 1 用 H100 实测定量了这件事：在云 GPU 上按 $3.85/卡时计价，把上下文从 16K 拉到 256K，每生成 1M 输出 token 的成本——

注意这个幅度，3.6×–7×，已经比得上激进的量化或结构化稀疏化带来的收益了。而且这件事被零售 token 价格藏起来了——厂商按「每 1M token 固定价」收费，你根本不知道输入长短对真实成本的影响。本地推理也一样：Figure 2 显示在 DGX Spark 上，多个模型的 inter-token 延迟在长 context 下直接翻倍，显存占用也翻倍。

二、长上下文从哪来

论文把长上下文的来源分成两类负载，这是全文的骨架：

  • LCW1 长程任务：任务需要很多步动作才能完成，每一步的模型输出和工具结果都被追加进对话，历史越滚越长。
  • LCW2 长输入任务：任务本身带一个很大的输入（长文档、长代码库），哪怕模型只做一次推理，输入就已经塞满了 context。

论文的核心论点：这两类负载都不需要「一直把整个历史/整个输入留在 context 里」。于是提出三个研究问题。

三、三个研究问题

四、四种上下文管理策略

论文定义了三种上下文管理策略，从「全留」到「每步重置」：

  • FHA（Full-History Accumulation）：基线，所有动作和观察都追加进一段对话，从不删。mini-swe-agent / mini-agent 的默认模式。
  • EoCC（End-of-Conversation Compaction）：对话撞到压缩阈值时，让模型产出一份「有界的、与任务相关的状态摘要」，开一段只含「原始任务 + 摘要」的新对话继续。阈值写成分「总 context 上限 / 压缩阈值」。
  • SAC（Single-Action Compaction）：最激进。每段对话只含「任务 + 当前语义状态」，模型恰好执行一个环境动作，观察结果，更新语义状态，然后整段丢弃，为下一步开新对话。

「短」的定义：相对 256K+ 的前沿窗口，16K–50K 就算短——这个量级本身已经能装下一整部《老人与海》。

五、问题 1：长程任务要长 context 吗

在 6 个长程基准上，用 EoCC 对照 FHA 基线。模型是 Claude Opus 4.5 和 GPT 5.6 Sol，阈值从 48K/36K 一路压到 16K/12K（部分到 8K/6K）。

准确率：Opus 4.5 相对基线在 −3.7 到 +5.6 个百分点之间摆动，GPT 5.6 Sol 在 −3.3 到 +4.4。关键是这两个区间看着吓人，但22 个阈值配置里，每个模型最多只有 5 个掉超过 2 个百分点。也就是说压到 16K/12K，绝大多数基准准确率几乎不变。

成本：Opus 4.5 省 2.2×–8.8×，GPT 5.6 Sol 省 2.4×–5.0×。这些是「只用短 context 窗口部署」带来的估算零售成本节省。

六、问题 2：长输入任务要长 context 吗

把长输入从对话里拿出来，存成文件（input01.txt、input02.txt），让 agent 用 sed / awk / head 选择性地读需要的部分——把长输入负载降成「长程 + 选择性阅读」。在 7 个长输入基准上对照「整段塞进去」的基线。

准确率：Opus 4.5 从 −0.4 到 +40.0 个百分点，GPT 5.6 Sol 从 +1.0 到 +30.9。注意是正区间为主——选择性阅读反而经常更好，因为模型不用在一堆无关文本里找信号。

成本：Opus 4.5 省 6.5×–54.6×，GPT 5.6 Sol 省 4.4×–233.3×。这是「选择性阅读 + 短 context 部署」的叠加。

对话长度：Figure 7/8 把对话总长对文档长度画图。文档长度轴是对数的，对话长度轴是线性的。y=x 参考线在这些坐标里是指数上升的，但实测对话长度几乎不随文档变长而增长——文档从 8K 到 2M，agent 实际读的量始终压在一个很窄的带里。这正是「输入大 ≠ 需要的信息多」的直接证据。

七、问题 3：每个 context 只取一个动作

SAC 是极端版：每段对话「任务 + 语义状态 → 恰好一个动作 → 观察 → 更新状态 → 整段丢弃」。在 SWE-bench Verified 和 Terminal-Bench 2.1 上测。

Opus 4.5 不仅没掉，Terminal-Bench 还涨了 4.6 分；GPT 5.6 Sol 小幅掉 2.0–3.3 分。但两个模型在每个 context 里只取一个动作、只带一份紧凑语义状态，峰值实时 context 从 130–200K 砸到 7–9K。这是「压缩频率推到相对极限，任务准确率却没有灾难性后果」的最强证据。

八、SSSM：语义状态空间模型

由问题 3 引出的概念：如果强模型靠频繁压缩甚至每步压缩还能保持性能，能不能所有长 context 工作流都被压成「单动作 + 语义状态」？论文提出 SSSM（Semantic State Space Model）：一个被后训练成（1）读懂自然语言状态描述、（2）推理下一个动作、（3）执行动作、（4）登记结果、（5）把结论/决策/结果写回状态描述——好让另一个全新推理实例能接力继续的模型。

它和传统 SSM（状态空间模型）的区别：SSM 在 token 之间维护的是黑盒神经状态，SSSM 维护的是可读的自然语言状态（所以叫「语义」）。论文还推断：SSSM 训练更省数据，因为不用教模型「去 context 的某个片段找答案」。最后抛出一句反问：那为什么要训练全历史累积模型？

九、不意的点

压缩是有损的。构造一个「工具抛硬币并汇报结果」的任务，压缩预算固定，agent 必然在某个压缩后丢掉早期某次硬币结果；若之后要查第 i 次结果，必然失败。所以论文结论不是「你永远不需要历史」，而是「你不需要把整段历史留在 context 里」。把对话历史存下来、用选择性阅读工具按需查，就把「查历史」降成了长输入任务——又回到了问题 2。这是全文逻辑自洽的关键一环。

十、面试怎么答

把全文串成一段可复述的答案：

长上下文贵，因为自回归生成的深度成本和 KV cache 都随 context 线性涨：云 GPU 上把窗口从 16K 拉到 256K，每生成 1M 输出 token 贵 3.6–7 倍，本地延迟直接翻倍，零售固定价把这层成本藏起来了。长 context 来自两类负载——长程任务（历史越滚越长）和长输入任务（输入本身就大）。论文证明前者用「对话撞到阈值就压缩成有界语义状态、开新对话」的 EoCC，把准确率守在 −4 到 +6 个百分点、成本省 2–9 倍；后者用「把输入存成文件、让 agent 选择性读」，准确率不降反升、成本省最高 233 倍，对话长度几乎不随文档变长。极端版 SAC「每个 context 只取一个动作」下，Opus 4.5 的 SWE-bench 持平、Terminal-Bench 还涨 4.6 分，峰值实时 context 从 130–200K 砸到 7–9K。它引出 SSSM：把状态存成可读的自然语言描述，让新推理实例接力，比全历史累积模型更省 token 也更省训练数据。唯一的意：压缩有损，所以结论是「不需要整段历史在 context 里」，不是「永远不用查历史」——查历史本身就是长输入任务。
