GPU 平均利用率已经 98%，训练却还能快 6 倍。Databricks 这篇博文完整记录了排查过程、算子变化与数据打包细节。以下为其全文翻译，文中的“我们”指原作者 Bruce Fontaine 和 Pardis Beikzadeh。

训练或微调一个数十亿参数的基础模型，需要大量算力，往往耗费数百乃至数千 GPU 小时。优化大模型训练性能并不容易，GPU 利用率这样的高层指标也未必能反映 GPU 实际用得有多充分。本文介绍如何穿透这些抽象层，在 AI Runtime 上把最新 Qwen 3.8 27B 模型的微调提速 6 倍——即便原来的 GPU 利用率已达到 98%，仍把固定数据集上的微调耗时从 7 小时 44 分钟压到 1 小时 17 分钟。

初始训练基准

基线模型在完整数据集上训练需 7 小时 44 分钟，训练期间 GPU 平均利用率显示为 98%，吞吐 9,396 token/s。

这个利用率看起来很高，但具误导性。标准 GPU 利用率只统计 GPU 处于工作状态的时间占比，无法告诉我们：GPU 活跃时，模型究竟把它用得有多充分。要弄清楚这一点，得继续往下看。

可以改进的地方

从这些表格里，可以发现当前模型存在几个整体性问题：

CPU 为每个训练步做准备的时间，比 GPU 执行它还长。这不太正常——GPU 执行时 CPU 侧操作通常是异步的，CPU 应当远远跑在 GPU 前面。主要影响是 GPU 会停下来等待，因此还有改进空间。

操作太多了！表格里有数十万个小操作。问题在于 CPU 无法以足够快的速度把 GPU 操作加入队列，让 GPU 持续忙碌。关键思路是减少 CPU 向 GPU 提交的操作数量。有几种通用方法，其中一种适合我们这次的情况：

  • torch 的 CUDA graphs 可以记录执行过的 CUDA 内核，再用一次 CPU 调用重放它们。很强大，但限制不少，且与 FSDP2 的动态行为冲突，暂不采用。
  • torch.compile 会追踪代码，并在可能的地方用 Triton 自动融合内核。本例将使用手动融合内核；对这些大模型操作，手动融合后就没有给 torch.compile 留下进一步优化的空间。
  • 手动融合内核针对特定操作使用专门的融合技术，是 torch 编译器无法自行应用的。好在社区已有不少成熟的预构建内核，例如 Flash Attention，它在本例中带来一点性能提升。

此外，批次中还有 padding 过多的问题：输入张量必须是矩形，每行都要补齐到该批次的最大 token 数。下文介绍一种适用于大模型的技巧，尽量减少这部分浪费。

融合内核

你可能注意到了，有些内核出现次数特别多。以 Qwen 为例，批量矩阵乘法内核在一个训练步中就运行了超过 30,000 次。

融合内核会把多个较小的 GPU 内核合成一个执行单元，避免 GPU 高带宽显存与片上存储之间代价高昂的数据搬运，同时让 GPU 核心的调度更高效。面对这么多额外内核，即使 torch.compile 能起作用，运行它也要花很长时间。因此先用手动融合内核减少操作总数，是一个不错的起点。Flash Attention 这类成熟的融合方案，也不是 torch.compile 自己能够发现的。

对于标准注意力层，transformers 默认用 torch 的缩放点积注意力（SDPA）。但那些小操作其实来自非标准的门控 Delta 网络层。幸运的是，针对这些层已有 causal-conv1d 和 flash-linear-attention 两种内核，可以融合每一层里的许多操作。我们怎么发现它们的？transformers 里 Qwen 的实现已经写明了支持哪些内核：

  • flash-linear-attention
  • causal-conv1d

获取这些内核主要有两种方式：

  • 自行安装：直接 pip 从 PyPI 安装（例如 flash-linear-attention），或 git clone 克隆仓库后编译；编译耗时过长时也可寻找提供预编译包的来源。
  • 使用 Hugging Face 的 Kernel Hub 获取预编译内核。

我们通常推荐第一种方式，尤其是结合 Docker 容器支持：在构建容器时就装好所有内核，以减少训练任务的启动时间。Kernel Hub 虽然方便，但内核往往明确依赖所安装的 torch 和 CUDA 版本，未必有适配当前配置的可用内核。这时 transformers 模型会静默回退到未经优化、性能较低的内核。

安装 flash-linear-attention 和 causal-conv1d 两个包后，端到端训练提速 3.7 倍，耗时降至 2 小时 5 分钟。表中高亮的新内核替代了前面表格里的逐元素函数，执行的操作总数也大幅下降，减至约原来的十五分之一：

批处理、分词与填充

现在 Qwen 已经相当快了，但还能再快一些。默认批处理方式采用二维矩形张量，长度为 8192 token（不发生 OOM 时的最大长度）。缺点是 padding 往往会浪费张量中相当多的空间。

如果 Qwen 只用标准注意力机制，torch 现在已提供较完善的 NestedTensor 支持，可完全移除 padding。但 flash-linear-attention 只支持更传统的一维打包张量方式：左侧是补齐后的二维批次，右侧是一维打包张量及边界偏移量。

不过不能随意这样做。预训练时直接把一维张量交给模型或许可以接受；但微调时，必须确保每个样本中的 token 只关注同一个样本内的 token。为此，需要将正确的样本 position_ids 传给模型，模型再把信息传给融合注意力内核，由内核应用正确的注意力掩码。

经过这个看起来很简单的改动，训练耗时从 2h05m 进一步缩短到 1h17m。原因有两个：

  • 主要原因：打包方式增加了每个批次中的序列数量，使总批次数减少了约 36%。这个比例取决于数据集中样本的长度及其分布。
  • 次要原因：Flash Linear Attention 内核需要针对每一种输入形状即时编译。此前输入形状动态变化，额外增加了几分钟编译时间。

取舍在于：这种改动会让输入流水线更复杂，且容易引入影响模型质量的错误。但在本例中，节省 36% 的批次值得这样做。还有其他减少 padding 的办法，例如保留原批处理方式、先按长度对所有输入排序以尽量减少填充——但这种排序可能让相邻样本出现意料之外的相关性，进而使模型产生偏差。

要点：当训练数据集中的输入短于模型可训练的最大 token 长度（本例 8192）时，高效地把数据打包成批次能节省大量时间。在这个数据集上获得 1.6 倍训练提速，耗时从 2h05m 降至 1h17m。

结论

本文介绍了如何将训练效率提升至 6 倍，归结为三点：（1）先测量真正重要的东西——不只看 GPU 利用率，还要看训练时间究竟花在哪里；（2）借助 Flash Linear Attention 等成熟库优化并融合内核；（3）针对模型调整数据批次的输入方式。

要规模化地做到这些，需要一个能把高性能路径变成默认选择的平台。AI Runtime（AIR）已内置许多改进：基础环境打包了最新的 CUDA 和 Flash Attention；自动跟踪 GPU 利用率、温度及健康状况等核心指标；确保 torch 和性能分析工具保持更新。其内部 Agent——Genie Code 也专门调优过，会寻找这类机会进一步优化训练。此外 UCVolumeDataset 还优化了从 Databricks 读取数据的过程。
